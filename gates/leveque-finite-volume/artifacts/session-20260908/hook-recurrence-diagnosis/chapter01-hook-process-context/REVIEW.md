# Stop-hook process context: confirmed settings and reproduction hypotheses

The matching public `rust-v0.153.4` source supports two important differences from a plain native-Python replay: **the hook shell is spawned suspended, assigned to a Job, then resumed; and hook environment values come from a persistent app-server snapshot.** It does not support a claim that the hook explicitly requests `CREATE_NO_WINDOW`. The installed binary reports `codex-cli 0.153.4`; its embedded source paths include `hooks\src\engine\command_runner.rs`. Matching version and source paths do not prove this app-server binary was built from byte-identical public source, so the actual host launch still needs reproduction/observation.

## Confirmed source behavior

- [Command runner, matching tag](https://github.com/openai/codex/blob/rust-v0.153.4/codex-rs/hooks/src/engine/command_runner.rs): local saved lines 216–241 set session cwd, three piped standard streams, kill-on-drop, and attempt Job-contained spawning. Containment failure falls back to flags 0 and normal spawn. Lines 420–424 clear the child environment, restore the saved snapshot, apply handler additions and scrub restricted names. Lines 428–453 default to COMSPEC/cmd.exe with `/C`, with raw quoting around the command; a configured shell can override that default. The actual configured `CommandShell` supplied by this desktop host has not been captured. Lines 283–293 release Job cleanup after successful completion; timeout/error uses process-tree cleanup. The outer timeout wraps waiting for the child output after stdin is written.
- [Job implementation](https://github.com/openai/codex/blob/rust-v0.153.4/codex-rs/utils/pty/src/win/job.rs): lines 43–53 configure `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE | JOB_OBJECT_LIMIT_BREAKAWAY_OK`. Lines 132–133 request `CREATE_SUSPENDED` (`0x4`); lines 175–191 spawn, assign with `AssignProcessToJobObject`, then call `NtResumeProcess`. No CPU, process-count or memory limit is configured there. `BREAKAWAY_OK` is a Job limit flag, **not** a request to launch with `CREATE_BREAKAWAY_FROM_JOB`. No `CREATE_NO_WINDOW`, `DETACHED_PROCESS` or `CREATE_NEW_PROCESS_GROUP` flag is requested by this path.
- [Hook registry](https://github.com/openai/codex/blob/rust-v0.153.4/codex-rs/hooks/src/registry.rs): lines 72–80 snapshot `std::env::vars_os()` when `Hooks::new` runs. Lines 92–98 preserve that same snapshot during reconfiguration. This is the then-current app-server process environment, not a fresh PowerShell profile or the later direct-exec environment. The hook command builder does not apply `shell_environment_policy` through `create_env`.
- [Environment scrubber](https://github.com/openai/codex/blob/rust-v0.153.4/codex-rs/protocol/src/shell_environment.rs): lines 13–20 and 33–49 remove exactly five names, case-insensitively: `CODEX_EXEC_SERVER_NOISE_AUTH_TOKEN`, `NODE_REPL_AUTH_TOKEN`, `OPENAI_FEDERATION_RULE_ID`, `OPENAI_IDENTITY_TOKEN_FILE`, and `OPENAI_WORKLOAD_IDENTITY_CONTEXT`. No `GIT_*` variable is inserted or scrubbed by these functions. In particular, the presence of `GIT_OPTIONAL_LOCKS` in other binary strings does not establish a hook override; those strings also occur in unrelated internal Git helpers.
- [Pipe execution helper](https://github.com/openai/codex/blob/rust-v0.153.4/codex-rs/utils/pty/src/pipe.rs), local lines 191–218: its ordinary pipe path spawns running, then assigns the process to a Job, accepting a documented descendant race. This contrasts with contained suspended spawning. It is not a complete trace proving which backend handled this particular `exec_command`. The read-only direct baseline in this folder reports actual Job membership, so “inside a Job versus outside one” alone is not an adequate diagnosis.

## Local bridge and guard

`C:/Users/qed_s/.codex/hooks.json` selects the explicit Python 3.12 ARM64 executable, `-B`, the native bridge and canonical guard, with an outer timeout of 30 seconds. The original failure record names the **inner gate command's 20-second timeout**, not the hook runner's 30-second timeout. The hook had progressed through the launcher and guard far enough to attempt that gate subprocess.

The native bridge reads stdin JSON, only normalizes top-level `cwd` and `transcript_path`, and calls the POSIX launcher with `subprocess.run(input=data)`. The launcher inherits the environment, prepends the isolated MSYS2 `usr/bin` to PATH, sets `MSYSTEM=MSYS`, preserves other inherited `MSYS` options while selecting `winsymlinks:sys noglob`, sets `PYTHONDONTWRITEBYTECODE=1`, and removes `PYTHONHOME`/`PYTHONPATH`. It invokes isolated Bash with `--noprofile --norc`; its shell entrypoint and `posix_exec.py` use exec to preserve POSIX interpreter identity and exact JSON-transported arguments. Neither Python layer specifies Windows creation flags, startup information or a Job object.

Thus inherited `GIT_*`, `HOME`, `USERPROFILE`, `XDG_CONFIG_HOME`, remaining PATH entries, `CYGWIN` and retained `MSYS` options can still differ. The isolated Git executable has PATH priority, but Git configuration selection and process behavior may still depend on those inherited values. The guard's closure launch, installed lines 728–735, captures stdout and merges stderr, sets `timeout=20`, and supplies no explicit environment or cwd override. The actual timed-out subprocess therefore inherits the guard's context.

The fresh [official hooks manual](https://learn.chatgpt.com/docs/hooks) confirms Windows command overrides, session cwd, stdin JSON, and timeout units. It does not specify creation flags or Job behavior. The downloaded manual and source copies are evidence artifacts, not changes to installed runtime/configuration.

1. Keep the exact payload, saved guard state, cwd, executable and command bytes fixed. If an actual configured shell is observed, reproduce that shell instead. `/C` alone is the source default; `/D` or `/S` would be extra experimental changes. Potential cmd AutoRun processing is a hypothesis, not an observed cause.
2. Reproduce the confirmed containment path: create the Job with only kill-on-close and breakaway-allowed flags; spawn the shell with `CREATE_SUSPENDED`; assign it before descendants can run; resume via `NtResumeProcess`; retain the Job handle through the run. Compare to ordinary running spawn plus later assignment. Record assignment/resume results, not merely final Job membership. Do not silently take a failed-assignment fallback as a successful contained test.
3. Compare a **small allowlist** of actual hook and direct environments: Git variables/config paths, home paths, PATH hash/order, `MSYS`, `MSYSTEM`, `CYGWIN`, and guard state directory. Record names/hashes rather than credentials or arbitrary environment values. Hook configuration refresh does not refresh the stored environment snapshot. A direct replay's environment cannot stand in for an observed hook snapshot.
4. If those controls still pass, inspect a slow gate child while it is alive: actual process tree, elapsed time, CPU versus waiting, and whether it has exited while a descendant retains its output pipe. The inner Python timeout covers subprocess communication, so a pipe-holder hypothesis is distinct from a gate computation that actually takes more than 20 seconds. No process-tree or pipe-holder cause has yet been observed here.
