# Git stat-cache diagnosis: source-supported mechanism, measurement pending

Use the isolated POSIX Git consistently for worktree/index operations during the next controlled measurement. Cross-runtime stat-cache replacement is a plausible explanation for the newly slow ordinary POSIX gate. It is not yet an established cause. Root reports an isolated MSYS Git diff running longer than 60 seconds, with about 36 CPU seconds and 95 MB read; that observation supersedes the earlier diagnostic limitation that only actual host Stop had reproduced the delay. Earlier frozen reports remain historical evidence.

The installed executables report native `git version 2.54.0.windows.1` and isolated `git version 2.55.0`. The isolated package metadata identifies `git-2.55.0-1` and `msys2-runtime-3.6.10-3`, x86_64. Matching public source versions establish a mechanism, not byte-identical build provenance or the values currently stored in this repository's index.

## Concrete mechanism

- Native [Git for Windows stat implementation](https://github.com/git-for-windows/git/blob/v2.54.0.windows.1/compat/mingw.c#L1328), saved lines 1328–1339 and 1385–1395, supplies zero inode, uid, gid and device fields, and derives `st_ctim` from Windows file creation time.
- The [MSYS runtime disk stat implementation](https://github.com/msys2/msys2-runtime/blob/msys2-3.6.10/winsup/cygwin/fhandler/disk_file.cc#L403), saved lines 403–432 and 478, uses change time for ctime (last-write fallback when unsupported), reports creation time separately as birth time, and obtains device, inode and ownership data. These conventions can differ for the same unchanged file. Current Git build configuration and actual affected entries still need measurement.
- Git [stat matching](https://github.com/git/git/blob/v2.55.0/statinfo.c#L24), lines 24–34 and 64–101, caches and compares these fields, subject to configuration/build flags. Its [content verification](https://github.com/git/git/blob/v2.55.0/read-cache.c#L233), lines 233–245 and 446 onward, can open and hash a file after cached stat information no longer suffices. Replacing one runtime's cache with the other's can therefore cause repeated content reads without a content change. This is an inference from the source paths, not a measured list of this repository's cache misses.
- Porcelain diff can itself replace cached stat data. [Git's configuration documentation](https://git-scm.com/docs/git-config#Documentation/git-config.txt-diffautoRefreshIndex) describes `diff.autoRefreshIndex`, enabled by default. Matching [native diff source](https://github.com/git-for-windows/git/blob/v2.54.0.windows.1/builtin/diff.c#L237) and [upstream diff source](https://github.com/git/git/blob/v2.55.0/builtin/diff.c#L237), lines 237–249 and 645–646, lock, reread, refresh and potentially write the index after stat-only matches. That refresh receives no pathspec, even when the requested diff uses exclusions. The excluded gate/ledger paths consequently do not by themselves bound this optional whole-index refresh.

## Important limit of optional-lock suppression

The [Git command documentation](https://git-scm.com/docs/git#Documentation/git.txt-GITOPTIONALLOCKS) says `--no-optional-locks` is equivalent to `GIT_OPTIONAL_LOCKS=0` and documents preventing status's optional index update. However, the matching diff paths inspected here have no `use_optional_locks()` guard: `refresh_index_quietly` calls `repo_hold_locked_index`, and [that helper](https://github.com/git/git/blob/v2.55.0/repository.c#L463) delegates directly to locking. The inspected lock implementation also has no such guard. Therefore this review does **not** certify that `git --no-optional-locks diff ...` preserves index bytes on these versions. A before/after index hash is required before relying on that claim. The option also cannot prevent index writes required by explicitly mutating commands such as staging or committing.

Do not change `core.checkStat`, `core.trustctime`, assume-unchanged bits or other freshness controls. Changing `diff.autoRefreshIndex` is unnecessary for the first experiment and could alter stat-only handling; preserve its current setting too. Optional-lock suppression, where actually honored, does not remove the cost of content comparisons needed by the requested operation and can prevent a cache from warming.

## Bounded measurement for root

After the current gate and all index writers finish, record index bytes/hash, executable versions and the small relevant configuration set. Serialize the same existing POSIX comparison twice with no intervening native worktree command; record elapsed time, CPU/read counts, output hash/exit and index changes. Then compare an otherwise identical sequence with the specific native read that previously intervened. Inspect selected cached stat fields before/after and the actual POSIX stat of the same unchanged files. A cache rewrite followed by renewed reads, with identical comparison output, would support the mechanism. Merely faster second runs could also reflect filesystem/object-cache warming and do not isolate it.

Preserve the released gate, exclusions, freshness semantics and timeout throughout. Root owns this measurement and any later operational choice. This review ran only executable version queries and source/document reads; it ran no diff, status, gate, refresh or index-writing command. Downloaded source and this additive packet are confined to the new local diagnosis directory.
